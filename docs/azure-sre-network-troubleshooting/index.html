Why it matters

The problem it solves.

When a connection fails, failed requests alone do not say whether an NSG denied the traffic or the application is down. Engineers end up guessing, or changing rules before the evidence is in.

  • Network or application

    Correlates VNet flow logs, NSG rules and independent health events to separate policy denial from a stopped service.

  • Every claim labeled

    Findings are marked as observed fact, configuration fact, inference or recommendation, with citations and gaps.

  • Read-only investigation

    The agent never changes NSGs, runs VM Run Command, restarts services or remediates.

  • Operators stay in charge

    Fault injection, restoration and cleanup are separate operator scripts, each approved by a human.

How it works

From trigger to approved change.

The same operating model as every use case in the showcase, applied to Azure SRE Network Troubleshooting.

  1. Trigger

    A connectivity complaint with endpoints, port and an exact UTC window

  2. Analyze

    Queries flows, NSG rules and health events, then labels each finding

  3. Approve

    A human reviews the recommendation and approves the restoration step

  4. Apply

    An operator runs the scoped restore script, then verifies fresh traffic

      Is it for you?
      
      
      Who it helps and what it takes.
      
      
      
      
        
      Who it's for
      • Cloud and network engineers
      • SREs rehearsing evidence-based investigation
      • Platform teams with a non-production Azure scope
      
        
      What you need
      • A dedicated non-production Azure subscription and approved costs
